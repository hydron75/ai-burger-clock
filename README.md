사용 경험 기록·설정·통계는 트레이 우클릭 메뉴에서도 이용할 수 있습니다. 상태 창의 X를 누르거나 다른 창으로 이동하면 작은 창만 숨겨지고, 앱은 트레이에 남습니다.

**2.6.0의 회복 알림:** 켠 뒤 첫 성공은 기준만 잡고, 같은 창에서 실제 사용 100% → 100% 미만이 새로 확인되면 Provider별로 한 번 알립니다. 캐시·리셋 예정 시각 경과·일반 사용량 감소만으로 알리지 않으며 일부 회복이 전체 서비스 사용 가능을 보장하지 않습니다. 추가 조회 없이 기존 주기를 따르므로 알림이 실제 회복보다 늦을 수 있습니다. OS 알림 허용·집중 지원 설정에 따라 배너가 보이지 않을 수 있습니다. **기본 꺼짐이며 이번 교체에서도 꺼짐을 유지했습니다.**

**2.8.0의 조기 초기화 알림:** 같은 Provider·창 ID·확인된 기간의 연속 성공 응답에서 원본 사용량이 **20%p 이상 감소하고 새 사용량이 10% 이하**, 이전 리셋까지 **5분 초과**, 리셋 시각 변경이 **1분 초과**, 두 성공의 간격이 **0분 초과~90분 이하**이며 양쪽 리셋이 창 길이와 모순되지 않을 때만 후보를 만듭니다. 첫 성공·캐시·중간 실패/취소·창 구성/기간 변경은 조용히 기준을 다시 잡습니다. 미사용 0% 창의 이동이나 예정 시각이 지난 정상 리셋은 알리지 않습니다. 원인은 확인되지 않으며 동일 구조의 계정·요금제 변경까지 구별할 정보는 없습니다.

이 설정은 회복 알림과 **독립된 기본 꺼짐**입니다. 켜도 조회를 추가하지 않으며 같은 성공 응답의 두 알림은 배너 하나로 합칩니다. Provider별 최신 확인 기록 **1건만 실행 중 메모리에** 보관하고, 사용량 변화·이전/다음 리셋·확인 기록의 나이는 로컬 Provider 상세에 표시합니다. 재시작하면 기록이 사라지며 OS 배너에는 수치·시각·식별자를 넣지 않습니다. Windows는 2.8.0, Mac은 후속 #73의 0.8.0에 반영됐습니다.

공식 페이지는 Windows 기본 브라우저로 열립니다. 미리 정해 둔 공식 주소만 사용하며, 가져온 공지 속 임의의 링크를 실행하지 않습니다.

**2.8.1의 현재 규칙(#82 병합 완료):** 주간 조기 초기화를 직전 성공 대비 원본 사용률 감소 + 이전 예정까지 5분 초과로 단순화합니다. 20%p·새 10%·90분 상한·리셋 변경 조건은 제거하고, 캐시의 마지막 성공으로 재시작 뒤 첫 새 응답도 비교합니다. Provider별 한 계정 전제와 기존 연속성/창 식별 검사는 유지합니다. 회복·배너·기본 꺼짐·조회 주기는 바꾸지 않으며 5시간은 조기 초기화 대상에서 제외합니다. 판정 진단은 별도 파일에 256건/128KiB 제한으로 기록합니다. [새 계약·오인 가능성·Mac 확인](QUOTA_EARLY_RESET_NOTIFICATIONS.md#82-병합-완료-주간-조기-초기화-조건-단순화-2026-10-20). 위 2.8.0 설명은 당시 기준입니다.

### 계정 한도는 어떻게 보나요?

**2.4.0**에서는 ‘한도 보기’를 누르면 같은 작은 창 안에서 **ChatGPT·Claude·Gemini**의 사용률·막대, 간략 리셋 시간, 마지막 성공·다음 조회 시각을 보여줍니다. 이전 2.3.0은 잔여율과 기존 카운트다운 표시였습니다. ChatGPT 제목 아래의 **Work/Codex**와 Gemini 아래의 **Antigravity · Gemini 모델**은 실제 조회 범위이며, 일반 ChatGPT나 Gemini Apps의 모든 한도를 뜻하지 않습니다. 이전 **2.2.4에는 ChatGPT와 Claude 한도만** 있었으며 Gemini 서비스 상태·기록·통계는 기존에도 있었습니다.

2.2.4부터 사용하는 **Provider별 흰 박스**와 제목 기준선, 박스 안 글자 시작 위치를 유지합니다. 한도 박스에는 hover 효과가 없으며 ‘한도 보기 ↔ 상태 보기’ 전환을 유지합니다. 이전 2.4.0의 창은 논리 374×518이고, **배포 2.4.1은 상태 카드의 마지막 확인 한 줄 때문에 374×569(+51 높이)**입니다. 사용량 막대·Provider 상세 동작은 추가로 바꾸지 않으며 한도 영역 안에서 세로로 스크롤합니다. 창 전체나 가로 스크롤은 아닙니다.

**2.5.0의 시간 비교:** 같은 막대 안에 회색 바탕 → 연한 시간층 → 진한 사용층 → 시간 경계선을 그립니다. 사용량이 시간층을 가려도 경계선은 남습니다. 시간층과 사용량은 마지막 성공 조회 시각에 고정하고, Provider 상세의 `균등 사용 기준보다 N%p 빠름/느림`과 `마지막 조회 기준, N분 전`으로 구분합니다. 합성 예로 시간 40%·사용 55%이면 15%p 빠름입니다. 실제 소진 시각 예측이나 창 시작 확인이 아닙니다. 이전 값·리셋 경과·기간/시각 미확인·5시간 창 사용 0% 등에서는 비교를 숨기고 상세에 사유를 표시합니다. 주간 0%는 유효한 기간이 있으면 비교합니다. 화면을 열 때 자동 조회하거나 창 높이·행 수를 늘리지 않습니다.

- 합성 예시 `45% 사용`이면 막대가 45% 채워집니다. 0%는 빈 막대, 100%는 가득 찬 막대이며 ChatGPT는 초록색, Claude는 주황색, Gemini는 파란색입니다. 이전 값·리셋 경과 값의 막대는 회색입니다. 응답에 있는 창만 표시하므로 주간 한도만 나올 수도 있습니다.
- 5시간 창은 `약 N시간 N분 후 리셋`, 주간은 `약 N일 N시간 후 리셋`으로 단순화합니다. 마지막 단위를 올림·이월한 뒤 값이 0인 단위는 앞뒤 모두 생략합니다. 1분 미만은 ‘곧 리셋 예정’, 시각이 없으면 ‘리셋 미제공’, 경과하면 ‘갱신 대기’입니다.
- 글자나 막대에 마우스를 올리면 **Provider별 하나의 상세 팝업**에 모든 창의 정확한 KST 리셋·한도 복원 예정 시각, 조회 상태·오류·정책·조회 범위를 표시합니다. 흰 배경·320 DIP 고정 폭·자동 줄바꿈·포인터 근처 배치이며 화면 경계를 벗어나지 않게 보정합니다. **2.5.1부터 10초 후 또는 클릭/Esc로 닫고, 그 Provider 박스를 벗어나기 전에는 다시 열지 않습니다.** Provider 박스 이탈·창 숨김에도 닫힙니다. 클릭은 원래 버튼에도 전달되며 긴 상세의 스크롤바 클릭도 닫힘 대상입니다. 휠 스크롤·문구 갱신으로 표시 시간이 연장되지 않습니다. 리셋 예정 시각은 실제 복원 보장이 아니며 새 조회로 확인합니다.
- **2.6.0의 키 처리 보완:** 일반 Esc는 위 닫힘 동작을 유지하되 **Alt+Esc는 상세 팝업 닫기로 소비하지 않고 OS 창 순환에 넘깁니다.** 창 전환으로 부모 창이 숨겨지면 기존 숨김 정리에 따라 상세가 닫힐 수 있으며, 이는 Alt+Esc 자체를 팝업 닫기 키로 처리하는 것과 다릅니다.
- 개발 브랜치의 기본 간격은 세 Provider 공통 **1시간**입니다. 어느 창이든 사용 **90% 초과~100% 미만인 경우도 1시간**, **정확히 100%이면 15분**, 알려진 리셋 **15분 전~15분 후에는 5분**마다 확인하며 Provider별로 가장 짧은 주기를 적용합니다. 화면에서 반올림된 글자가 아니라 원본 수치로 판정하고, 새 조회에서 회복되면 확인된 사용량에 맞는 주기로 돌아갑니다. 기본 예약은 `Regular`, 사용 90% 초과 예약은 `LowRemaining`으로 기록해 같은 1시간이어도 이유를 구분합니다. 배포 2.7.0까지의 기본 간격은 6시간이었습니다.
- **#63 병합 완료·2.7.0에 반영·배포 완료:** Gemini의 정확한 원본 사용 0% 창은 새 빠른 조회 리셋 기준에서 제외합니다. 실제 사용에서 얻은 이전 리셋 +15분은 유지하며 구형 캐시의 출처 불명 목록만 한 번 정리합니다. 세 Provider의 예약 이유·선택 리셋·예약/다음 조회 시각을 앱 데이터의 `logs/quota-polling-diagnostics.json`에 최근 256건·128KiB로 제한해 기록하고, 1분 이내 흔들림은 구간 양끝만 보존합니다. [전환 제약·진단 위치/확인 방법·양쪽 검사](GEMINI_ANTIGRAVITY_QUOTAS.md#후속-개발-미사용-창의-잦은-조회-방지). 진단 원문에는 실제 리셋 시각이 있어 공개하지 않습니다. 예약 결정 기록이지 실행 트리거 이력은 아닙니다.
- 한도 조회가 실패하면 **15분 → 30분 → 1시간**, 이후 최대 **1시간** 간격으로 재시도하되 평소 주기를 넘지 않습니다. 마지막 확인 사용률이 100%라면 실패가 이어져도 15분을 넘지 않습니다. 리셋 구간의 더 빠른 조회가 우선이고, 성공하면 실패 횟수를 초기화합니다.
- 앱 시작·절전 복귀 때 바로 확인합니다. 연결 복구는 네트워크 변화 뒤 **5초** 기다렸다가 공식 상태와 계정 한도를 함께 확인합니다. 기다리는 중 다시 바뀌면 마지막 변화부터 5초를 기다리고, 직전 연결 복구 조회 후 1분 이내의 변화는 버리지 않고 1분 시점으로 미룹니다. 대기 끝에 사용 가능한 연결이 없으면 해당 조회를 건너뛰며 1분 제한도 쓰지 않습니다. 이 판정은 인터넷·DNS 접속 성공까지 보장하지 않습니다. 카운트다운 자체는 인터넷을 사용하지 않습니다.
- 기존 Refresh와 트레이의 **‘상태·한도 새로 고침’**은 세 Provider 한도와 공식 상태를 함께 갱신합니다. 한도 조회 중에도 공식 상태를 새로 고칠 수 있으며, 이미 조회 중인 한도는 중복 실행하지 않습니다. 공식 상태 자체가 조회 중일 때는 Refresh 버튼이 잠시 비활성화됩니다.
- 조회 실패는 ‘조회 불가’ 또는 ‘이전 조회값’입니다. 리셋 예정 시각이 지나도 임의로 사용률을 0%로 바꾸지 않고 ‘갱신 대기’로 표시합니다. 성공 시각은 CLI 응답을 받은 시각이지 서버 데이터 생성 시각을 보장하지 않습니다.
- 인증은 각 공식 CLI가 관리합니다. 이 앱은 인증 파일·쿠키를 직접 읽거나 비공개 HTTP API를 호출하지 않습니다. Claude는 모델 턴·토큰·보고 비용 0인 `/usage` 결과만 받습니다.

한도 부족을 서비스 장애로 표시하거나 트레이 색상·시간표·실측 통계를 바꾸지 않습니다. 크레딧 처리, 리셋권 조회·사용, 예정 리셋 시각 도달만으로 내는 알림, 자동 작업 실행, 일반 ChatGPT 모델별 메시지 한도는 포함하지 않습니다. Claude의 실험적 응답이 누락될 수 있는 제한과 실제 확인 결과는 [상세 기록](ACCOUNT_QUOTAS.md)을 참고하세요.

- **제약:** agy에는 이 실행만 사용자 hooks·MCP를 제외하는 공식 옵션을 확인하지 못했습니다. 기존 설정을 읽거나 초기화할 수 있다는 제한을 사용자가 수용한 조건입니다. 자동 업데이트 차단·입력 닫기·제한시간·0턴/0토큰 응답 검증을 적용하지만 완전한 설정 격리나 모든 실행의 절대 비소비를 보장하지 않습니다.
- Windows는 **한도 보기 전환 방식을 유지**합니다. 제목은 박스 밖, 각 Provider는 별도 흰 박스에 표시합니다. 창 크기는 그대로이며 세 Provider 한도는 한도 영역 안에서 세로로 스크롤합니다. 클릭할 수 없는 한도 박스에는 hover 효과를 넣지 않았습니다.

2026-10-09 KST 준비 단계에서 이 PC의 agy **1.3.2 / 종료 코드 0**을 확인하고 후보 클라이언트로 **Gemini만 실제 조회**했습니다. 8.37초에 5시간·주간 두 한도 창을 받고 정상 종료·0턴/0토큰 응답 검증을 통과했습니다. 승인 뒤 배포한 2.3.0의 Gemini 박스와 값 정상 표시도 사용자가 확인했습니다. 합성 10초 응답성 검사·실계정 단독 조회·실제 화면 확인은 [2.3.0 배포 기록](MAINTENANCE_2_3_0.md)에서 구분합니다. CLI 응답 수신이 서버 데이터 원래 생성 시각·실시간 갱신을 보장하지 않습니다.

## 4. F/B와 색상은 서로 다른 뜻입니다

**문자는 시간표, 색상은 주의할 정도**입니다.

- **F:** FULL THROTTLE. 미국 업무시간을 피한 구간입니다.
- **B:** BURGER TIME. 미국 업무시간과 겹치는 구간입니다.

색상은 다음 순서로 결정합니다. 위쪽 조건이 있으면 아래쪽보다 우선합니다.

| 색상 | 뜻 |
|---|---|
| 빨강 | 하나 이상의 Provider에 일부 또는 주요 장애가 확인됨 |
| 주황 | 위 장애 없이 성능 저하가 있음. 또는 모두 정상이지만 BURGER TIME임 |
| 회색 | 확인된 장애·성능 저하는 없지만, UNKNOWN/STALE가 있는 Provider가 있음 |
| 초록 | FULL THROTTLE이고 모든 Provider가 공식 정상임 |

예: **주황색 F**는 “시간표는 좋지만, 확인된 서비스 문제가 있다”는 뜻입니다.

마우스를 아이콘 위에 올리면 다음 전환까지 남은 시간과 세 Provider의 개별 권고가 나옵니다. **빨간 아이콘 하나가 세 서비스 모두의 장애를 뜻하지는 않습니다.**

## 5. GO, HOLD, STOP, CHECK는 무엇인가요?

| 시간표 | 해당 Provider의 공식 상태 | 앱의 권고 |
|---|---|---|
| FULL | 정상 | GO — 새 대형 작업을 시작할 후보 시간 |
| FULL | 성능 저하 | HOLD — 새 대형 작업은 잠시 미루기 |
| FULL | 일부·주요 장애 | STOP — 해당 Provider에서 새 대형 작업 시작을 피하기 |
| FULL | 확인 불가·오래된 정보 | CHECK — 공식 상태를 직접 확인하기 |
| BURGER | 정상 | BURGER TIME 유지 |
| BURGER | 성능 저하·장애 | BURGER + ISSUE — 시간표와 서비스 모두 주의 |
| BURGER | 확인 불가·오래된 정보 | BURGER + CHECK — 시간표 주의, 공식 상태 확인 필요 |

STOP은 **권고 문구**입니다. 앱이 다른 AI 프로그램을 강제로 막거나, 이미 실행 중인 작업을 종료하지는 않습니다.

공식 상태는 보통 5분 간격으로 확인합니다. 현재 배포 2.7.0도 2.4.1에서 개선한 다음 표시를 유지합니다.

- **UNKNOWN:** 아직 응답을 받지 못했거나, 응답은 받았지만 상태·사건 범위를 판정할 수 없습니다.
- **STALE:** 필요한 공식 응답의 마지막 수신 성공 뒤 15분 이상 지났습니다. “장애 확정”이 아니라 “새 정보가 필요함”입니다.

‘최근 조회 시도’는 응답 수신 성공 시각과 다릅니다. Provider 상태 글자 위에 마우스를 올리면 마지막 확인 시각과 수신·판정 실패 이유를 따로 볼 수 있습니다.

2.2.4의 상세 도움말은 값이 없는 관련 구성요소·사건·사건 ID·마지막 알려진 상태·출처 줄을 숨깁니다. 최근 조회·성공 시각은 유지하며, 트레이 카운트다운도 기존 초 단위입니다.

**2.4.1에 반영:** 카드의 ‘마지막 확인’은 필요한 공식 응답을 모두 받은 시각입니다. 사건 범위를 판정할 수 없어도 이 시각은 갱신하므로 새 응답이 계속 오면 UNKNOWN / CHECK이지 STALE가 아닙니다. 응답 수신이 15분 이상 끊기면 STALE가 됩니다. Tooltip은 현재 판정·수신/판정 실패·과거 판정 상태·범위 미확인 사건을 구분하며, 지난 장애를 현재 카드에 그대로 남기지 않습니다. 응답 수신 성공이 서비스 정상이나 서버 자료 최신성 보증은 아닙니다.

## 6. 왜 어떤 날은 22시, 어떤 날은 23시인가요?

한국의 10시·22시를 고정해 놓은 시계가 아니기 때문입니다.

기준은 미국의 월~금 각 업무일입니다.

> 미국 동부 오전 9시부터, 같은 미국 날짜의 서부 오후 6시까지를 BURGER TIME으로 봅니다.

미국은 계절에 따라 시계를 한 시간 바꾸는 **서머타임(DST)**을 사용합니다. 앱은 Windows의 시간대 정보를 사용하므로 사용자가 한 시간씩 고칠 필요가 없습니다.

아래는 공휴일이나 DST 전환이 끼지 않은 보통의 주입니다.

| 미국 시간 모드 | 한국에서 보이는 BURGER 구간 | 주말에 이어지는 FULL 구간 |
|---|---|---|
| 서머타임(DST) | 22:00~다음 날 10:00 | 토요일 10:00~월요일 22:00 |
| 표준시간(Standard) | 23:00~다음 날 11:00 | 토요일 11:00~월요일 23:00 |

시계가 바뀌는 주말에는 연속 FULL이 59시간 또는 61시간일 수도 있습니다. 카운트다운은 실제 다음 전환 시각을 사용합니다.

### 공휴일 보정은 무엇을 바꾸나요?

기본값은 **ON**입니다. 미국 정기 연방 공휴일 11종과 대체휴일에 해당하는 업무 구간을 시간표에서 뺍니다.

예를 들어 미국 월요일이 대상 공휴일이면, 금요일 업무가 끝난 뒤의 FULL이 화요일 업무 시작까지 이어질 수 있습니다.

- 토요일 공휴일은 앞 금요일, 일요일 공휴일은 다음 월요일을 쉬는 일반적인 월~금 근무 규칙을 사용합니다.
- 한국 날짜 하루 전체를 FULL로 바꾸는 방식은 아닙니다.
- 창에 ‘주말+공휴일’ 또는 ‘공휴일’이 표시됩니다. 다음 전환 글자 위에 마우스를 올리면 반영된 공휴일 이름을 볼 수 있습니다.
- 설정을 끄면 기존의 “주말만 제외하는 시간표”로 돌아갑니다. 선택은 재시작 후에도 유지됩니다.

회사별 휴가, 주·지역 공휴일, 임시 휴무, 반일 휴무는 포함하지 않습니다. **연방 공휴일이라고 AI가 반드시 한산한 것은 아닙니다.** 자세한 범위는 [공휴일 정책 설명](HOLIDAYS_TRAY.md)에 있습니다.

## 7. 내 경험을 기록하고 통계 보기

Provider 행을 우클릭해서 하나를 고릅니다.

| 기록 | 내가 느낀 결과 |
|---|---|
| Success | 잘 끝났어요 |
| Slow | 느렸어요 |
| Error | 오류가 났어요 |
| Interrupted | 도중에 끊겼어요 |

앱은 그때의 시각, 시간표, DST, 공휴일 설정, 공식 상태와 권고를 함께 적어 둡니다. 메모는 선택 사항입니다.

메모는 저장할 때 앞뒤 공백을 정리한 뒤 최대 1,000 UTF-16 단위까지 보관합니다. 이모지·결합 문자를 중간에서 자르지 않으므로 경계에 따라 999자 등으로 저장될 수도 있습니다. **실제로 잘렸으면 ‘앞부분 N자만 저장’ 안내**를 표시하며, 1,000자 이하나 공백만 정리된 경우는 기존 ‘저장됨’ 안내를 유지합니다. 입력 중에는 잘라 버리지 않고 저장 시 한 번만 적용합니다.

공식 장애 중에도 내 작업이 성공했다면 Success로 기록하면 됩니다. 공식 정상이지만 내가 오류를 겪었다면 Error로 기록하면 됩니다. 두 정보는 서로를 덮어쓰지 않습니다.

Statistics에서는 최근 7일·30일·전체 기록을 볼 수 있습니다. Provider별, 한국 시간대별, FULL/BURGER별, 주말·공휴일별, DST/표준시간별로 나눠 봅니다.

- **n = 3:** 직접 남긴 기록이 세 개라는 뜻입니다.
- **No data:** 그 구간에는 기록이 없습니다. 성공률 0%라는 뜻이 아닙니다.
- 30개 미만이면 소표본 안내를 표시합니다. 30개가 넘었다고 자동으로 결론이 확실해지는 것은 아닙니다.

2.1.2부터 알 수 없는 Provider 이름처럼 해석할 수 없는 일부 기록은 통계에서 건너뛰고 ‘읽을 수 없는 기록 N건 제외’로 알립니다. 원본 기록을 삭제하는 것은 아니며, 모든 DB 손상을 자동으로 복구하는 기능도 아닙니다.

**이 통계는 ‘기록한 경험의 비율’이지 ‘모든 AI 작업의 오류율’이 아닙니다.** 문제를 겪을 때만 주로 기록했다면 결과도 그쪽으로 치우칠 수 있습니다.

공휴일 ON/OFF와 이전 버전의 미기록 데이터를 구분합니다. 정책 효과를 비교할 때는 정책별 FULL/BURGER 행을 보세요. 전체 행에는 서로 다른 정책의 기록이 섞일 수 있습니다.

## 8. 기록은 어디에 있나요?

이 PC의 다음 파일에 저장합니다.

~~~text
%LOCALAPPDATA%\AIBurgerClock\burgerclock.db
~~~

SQLite는 **파일 하나를 중심으로 쓰는 작은 기록장**이라고 생각하면 됩니다. 사용 중에는 옆에 임시 관리 파일이 생길 수 있습니다.

사용 기록을 외부로 전송하지 않습니다. AI 답변·프롬프트·계정 식별 정보·쿠키·인증 토큰을 저장하지 않습니다. 한도 조회의 인증은 공식 CLI에 맡기며 이 앱은 인증 파일을 직접 읽지 않습니다. CLI의 전체 출력 대신 검증한 한도 수치·기간·리셋 시각만 사용합니다. 직접 쓰는 메모에도 민감한 내용은 넣지 마세요.

백업하려면 먼저 트레이 메뉴에서 앱을 정상 종료한 뒤 기록 파일을 복사하세요. 파일을 삭제하면 새 빈 기록장이 만들어지지만, 지운 기록이 복구되는 것은 아닙니다.

2.2.0도 기록장의 구조는 schema 2입니다. 계정별 마지막 성공값은 기존 AppMetadata에 최대 두 항목으로 덮어써서 보관하며, 사용 경험·공식 상태 이력의 구조는 바꾸지 않습니다. 이전 schema 1을 처음 열 때는 같은 폴더에 자동 백업한 뒤 업그레이드합니다. 과거 기록의 판정은 새 규칙으로 덮어쓰지 않습니다.

저장 오류가 있으면 창 아래에 안내합니다. 같은 오류가 매초 새로운 ‘저장됨’ 안내를 덮어쓰지 않으며, 오류가 해소되면 남아 있는 오류 표시를 지웁니다. DB 자체를 자동으로 복구하는 기능은 아닙니다.

Provider별 공식 상태 저장 실패도 따로 기억합니다. 예를 들어 ChatGPT 상태 저장이 실패했다면, Claude 저장이 성공했다는 이유만으로 그 오류를 지우지 않습니다. 이는 로컬 저장 문제이며 해당 AI 서비스의 장애 판정과는 별개입니다.

2.2.4는 중복 Provider 입력 진단을 `%LOCALAPPDATA%\AIBurgerClock\logs\status-ticker.log`에 남깁니다. 파일당 64 KiB, 이전 파일 1개만 보관하며 정상 입력에는 로그를 만들지 않습니다. 사용자 기록 DB와는 별도이고, 로그 쓰기 실패가 화면 갱신을 멈추지 않습니다. DB 구조는 schema 2 그대로입니다.

**2.0.x로 돌아가려면 이전 DB 백업도 필요합니다.** EXE만 옛 버전으로 바꾸면 새 DB 구조를 읽지 못합니다. 현재 DB까지 보존한 뒤 복원하세요. [백업·복원 상세](HOLIDAYS_TRAY.md)

## 9. 자주 헷갈리는 점

**인터넷이 끊기면 앱도 멈추나요?**  
아니요. 시간표·카운트다운·로컬 기록은 계속 쓸 수 있습니다. 공식 상태는 UNKNOWN/STALE로 표시될 수 있습니다.

**알림은 언제 오나요?**  
시간표가 실제로 전환될 때, FULL 중 Provider 권고가 GO/HOLD/STOP 사이에서 의미 있게 바뀔 때, 공휴일 설정을 바꿀 때입니다. 같은 상태를 반복해서 알리지는 않습니다. 앱 시작 자체로 무조건 알림을 띄우지는 않습니다.

**절전 중에도 알림이 오나요?**  
절전 중에는 표시하지 못합니다. 복귀 후 현재 시간표가 이전과 달라졌으면 알립니다. 2.1.1부터 복귀 시 공식 상태의 즉시 재조회를 요청합니다. 이미 조회 중이면 그 조회가 끝난 직후 한 번 더 확인합니다. 인터넷 연결이 아직 복구되지 않았다면 조회가 실패할 수 있습니다. Windows 알림 설정에 따라 화면에 보이지 않을 수도 있습니다.

**자동 시작을 켰는데 옛 버전이 실행돼요.**  
사용할 파일을 먼저 실행한 뒤 자동 시작을 체크하세요. 현재 실행 파일의 경로로 등록합니다. 앱은 다른 경로나 Windows 차단 상태를 표시하지만, 최종 확인은 작업 관리자의 시작 앱 상태와 실제 실행 파일 위치도 함께 봐야 합니다. 레지스트리 숫자를 임의로 고치지는 마세요.

**공식 정상인데 왜 내가 쓰는 AI는 느릴까요?**  
공식 공지는 늦을 수 있고, 계정·지역·기능별 차이도 있습니다. 특히 Gemini는 Workspace 상태 페이지의 Gemini 제품 범위를 봅니다. 모든 Google AI 서비스가 포함되는 것은 아닙니다.

## 10. 직접 코드를 빌드하고 싶다면

이 부분은 개발할 때만 필요합니다. 현재 UI는 WinForms, 대상은 `net10.0-windows10.0.19041.0`, 실행 환경은 x64입니다.

Visual Studio Community 2026의 .NET 데스크톱 개발 워크로드 또는 .NET 10 SDK를 사용합니다. `AiBurgerClock.sln`을 열거나, 프로젝트 폴더의 PowerShell에서 실행하세요.

~~~powershell
.\build.ps1
~~~

빌드와 자체 검사를 합니다. 배포용 단일 EXE까지 만들려면, 실행 중인 앱을 먼저 종료한 뒤 다음 명령을 사용합니다.

~~~powershell
.\build.ps1 -Publish
~~~

- 일반 빌드: `bin\Release\net10.0-windows10.0.19041.0\win-x64` — 폴더 전체가 필요합니다. #86 이전 2.8.1 소스 빌드는 `net10.0-windows` 폴더입니다.
- 배포본: `dist\win-x64\AI Burger Clock.exe` — .NET 런타임은 별도로 필요합니다.
- 직접 추가한 패키지는 `Microsoft.Data.Sqlite 10.0.12` 하나입니다. 함께 필요한 SQLite 부품은 패키지 관리자가 가져옵니다.
- 경고도 빌드 실패로 취급하고, 검사 프로그램이 실제로 끝난 결과까지 확인합니다.
- `-Publish`는 고유한 임시 폴더에서 단일 EXE를 만든 뒤 그 EXE의 자체 검사를 통과해야 `dist`에 반영합니다. publish·검사 실패 때는 기존 EXE를 유지하고, 교체 실패 뒤 복원까지 실패하면 복구용 이전 EXE의 보관 경로를 오류에 표시합니다. 이 절차는 별도의 사용자 DB/배포 백업을 대신하지 않습니다.

개발용 검사 명령과 주의사항은 [소스 해설의 검사 안내](CODE_GUIDE.md)에 있습니다. 특히 자동 시작 설정을 바꾸는 검사는 별도 옵션이므로 일반 사용 중에는 실행할 필요가 없습니다.

Windows smoke와 수동 테스트 빌드는 PR별 산출물 폴더에서 직접 실행하지 않고, [고정된 변경 전·후 테스트 실행 경로](WINDOWS_TEST_RUNNER.md)를 사용합니다. `test-windows.ps1`은 실행 파일 묶음의 해시를 확인하고, 로그·합성 PNG는 PR별로 보관하며 반복 실행 후 트레이 기록 증가 여부를 읽기 전용으로 확인합니다. 배포 EXE는 교체하지 않습니다.

**Windows 2.8.3의 한도 알림(#86에서 도입):** 회복·조기 초기화 한도 알림만 센터에 보관하는 토스트를 사용합니다. 기본 self-test·smoke는 실제 풍선/토스트·운영 등록 없이 가짜 발송기로 검증합니다. 별도 시험 ID 통합 검증, 실제 배포 경로의 명시적 운영 등록과 해제·dry-run, 민감한 내용 없는 발송 진단은 [Windows 한도 알림 안내](WINDOWS_QUOTA_NOTIFICATIONS.md)를 따릅니다. 등록은 자동 시작과 별개이며 일반 시작·검사·COM 콜백이 운영 등록을 만들거나 복구하지 않습니다. 2.8.2에서 만든 운영 등록은 같은 배포 경로이면 재등록하지 않습니다. 이번 대상 확인·해제 dry-run과 배포 결과는 [2.8.3 기록](MAINTENANCE_2_8_3.md), 처음 등록한 결과는 [2.8.2 기록](MAINTENANCE_2_8_2.md)에 둡니다.
