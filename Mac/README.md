## 0.8.1: 공통 대기 알림 판정 반영과 .NET 런타임 10.0.13

0.8.0 이후 변경을 모은 유지보수 빌드입니다. 화면·메뉴·알림 문구·설정은 바뀌지 않습니다.

- **공통 대기 알림 판정(#74):** 회복·조기 초기화 대기 알림을 표시 직전에 다시 확인하는 판정을 공통 `QuotaPendingAlertPolicy`로 옮겼고, Mac은 `Current`에서 그 함수만 호출합니다. 큐·종류별 토글·6.5초 간격·전달은 그대로입니다.
- **.NET 10.0.402 / 런타임 10.0.13:** 이 번들에 들어가는 .NET 런타임이 10.0.12에서 10.0.13으로 올라갔습니다(번들의 `System.Private.CoreLib` 버전으로 확인).
- 문서만 바뀐 #75(조회 트리거 진단 후보 정리)는 코드에 영향이 없습니다.
- 빌드는 지금도 Xcode 27.1과 .NET macOS 워크로드 27.0.10722의 지원되지 않는 조합이라 `--allow-xcode-mismatch`로 만들었습니다. [기록](../MACOS_PORT.md#53-081-정리)

## 0.8.0: 한도 조기 초기화 알림 연결과 기본 조회 1시간

Windows 2.8.0에 배포된 공통 변경 두 가지를 Mac 앱에 포함합니다: 계정 한도의 기본 조회 간격 1시간(#68)과 한도 조기 초기화 알림(#70). 판정·문구·설정 키·합쳐진 배너는 공통 원본이고, Mac은 메뉴·알림 전달·메인 스레드 전환·종료 정리만 연결합니다. 회복 알림 컨트롤러를 확장해 두 알림을 함께 다룹니다. [기록](../MACOS_PORT.md#52-080-정리)

- **켜는 곳**: 오른쪽 클릭(또는 control-클릭) 메뉴의 **한도 조기 초기화 알림**. **한도 회복 알림 바로 다음**에 있습니다(Windows 트레이 메뉴와 같은 상대 순서). 기본 꺼짐이고 회복 알림과 **서로 독립**입니다. 켜도 추가 조회는 하지 않고, 켠 뒤 첫 성공 조회는 기준만 설정합니다.
- **알리는 때**: 같은 Provider의 연속된 성공 조회 둘을 비교해 **사용량이 20%p 이상 줄어 10% 이하가 되고**, 이전 리셋까지 5분을 넘게 남았는데 **리셋 예정 시각이 1분을 넘게 바뀐** 창이 있으면 "예정보다 일찍 초기화된 것으로 보입니다"로 알립니다. 원인은 단정하지 않습니다. 성공 간격이 90분을 넘거나 중간에 조회가 실패·취소됐거나 창 구성·길이가 바뀌면 알리지 않고 새 기준을 잡습니다. 첫 조회, 정상 예정 리셋, 미사용 0%에서 리셋이 움직이는 경우는 제외합니다.
- **알림 내용**: 비율·시각 없이 창 이름만 씁니다. 회복과 조기 초기화가 **같은 조회 응답**에서 함께 성립하면 Provider별 **배너 하나**로 합쳐 조기 초기화 문구를 앞세웁니다. 회복 알림 단독 문구는 그대로입니다.
- **기존 알림이 먼저**: 시간표·공식 상태·공휴일 알림을 먼저 요청하고 한도 알림은 그 뒤 약 6.5초 간격을 둡니다. 대기 중에 조회가 실패하거나 연속성이 끊기거나 창이 바뀌거나 다시 소진되거나 90분이 지나거나 설정을 끄면 대기 중인 알림은 사라집니다. Provider마다 최신 요약 하나만 보관합니다.
- **Provider 상세**: 이번 실행 중 확인한 마지막 조기 초기화 가능성이 해당 Provider 상세(툴팁)에 "최근 조기 초기화 가능성"으로 나타납니다. 당시 사용량 전/후와 이전·다음 리셋 예정 시각은 이 로컬 상세에만 있고 알림에는 없습니다. 앱을 다시 시작하면 사라지며 디스크에 쓰지 않습니다. 한도 행·막대·팝오버 높이(380×821pt)는 그대로입니다. VoiceOver는 기존 툴팁 경로를 따릅니다.
- **기본 조회 1시간(#68)**: 기본 조회 간격이 6시간에서 1시간이 됩니다(0.7.0까지는 6시간). 사용 90% 초과~100% 미만도 1시간, 정확히 100%는 15분, 리셋 전후 15분은 5분, 실패 재시도는 15분부터 최대 1시간입니다. Provider 상세의 정책 안내도 바뀝니다. 감지 지연은 최대 약 1시간입니다. 진단 파일은 `Regular`(기본)와 `LowRemaining`(90% 초과)을 구분해 기록합니다.
- **알림 권한**: macOS 알림을 허용하지 않아도 조회와 앱은 그대로 동작합니다. 허용하지 않은 상태에서 켜면 배너가 표시되지 않는다는 안내가 나옵니다.
- **한계**: 앱이 꺼져 있거나 절전 중에 일어난 초기화와 성공 간격이 90분을 넘는 초기화는 감지하지 못합니다. 실행 중 계정이나 요금제를 바꾸면 앱을 다시 시작해야 기준이 초기화됩니다. 정상 응답 수신 시각은 서버 데이터 생성 시각을 보장하지 않습니다.

## 0.7.0: Gemini 모델 전용 주간 행과 잦은 조회 방지

0.6.0 이후 main에 들어가 Windows 2.7.0에 배포된 공통 변경 두 가지(#62, #63)를 Mac 앱이 그대로 받습니다. 판정·문구·조회 정책은 공통 원본이고 Mac 화면 코드는 바뀌지 않았습니다. Mac에서는 검사(smoke)만 늘렸습니다. [기록](../MACOS_PORT.md#49-070-정리)

- **Gemini 모델 전용 주간 행(#62)**: `agy`의 `/usage`에 모델 전용 주간 한도가 따로 있으면 Gemini 박스에 `5시간` → `주간` → `주간 {묶음 이름}` 순서로 행이 늘어납니다. 모델 이름을 고정하지 않고 응답의 묶음 이름을 그대로 씁니다. 모델 전용 행이 없는 기존 응답은 그대로이며, 행 문구·막대·시간 비교·VoiceOver 읽기도 다른 주간 행과 같은 형식입니다. [기록](../MACOS_PORT.md#47-gemini-모델-전용-주간-행62-확인과-smoke-시나리오)
  - 한도 영역은 최대 340pt이고 모델이 늘어도 팝오버는 더 커지지 않습니다. 넘치는 행은 한도 영역 안에서 스크롤합니다(5시간+주간 2행 → 3행에서 821pt → 835pt, 1280×800에서 751pt, 1024×640에서 591pt 잘림 없음).
  - **알려진 한계**: 행은 한 줄이라 모델 이름이 길면(대략 40자 안팎부터) 줄 끝의 `N% 사용 · 약 N일 후 리셋`이 `…`로 잘립니다. 막대·Tooltip·VoiceOver 문구는 전체를 유지합니다. 표시 규칙이 걸린 사항이라 Windows와 정한 뒤 바꿉니다.
- **미사용 창의 잦은 조회 방지(#63)**: Gemini에서 사용 0%인 창의 리셋은 5분 간격 빠른 조회의 기준에서 제외합니다. 리셋이 응답마다 앞으로 밀리는 미사용 창 때문에 `agy`가 하루 수백 번 실행되던 것을 막기 위한 변경입니다. 실제 사용이 있는 창의 리셋, 다른 Provider, 기본 6시간(0.7.0 당시. #68 이후 1시간)·실패 재시도·수동 Refresh·절전 복귀는 그대로이며, Provider 상세에 이 예외를 설명하는 한 줄이 추가됩니다.
  - Claude에서 1초 안팎으로 흔들리던 리셋 기준 시각은 1분 이내 묶음의 양 끝만 남겨 정리합니다.
  - 이전 버전에서 저장한 Gemini 캐시는 처음 실행할 때 한 번 정리됩니다. 한도 값과 마지막 성공 시각은 그대로입니다.
- **조회 예약 진단 기록(#63)**: 세 Provider가 다음 조회를 정할 때마다 예약 이유·선택된 리셋·조회 시도·다음 조회 시각을 `~/Library/Application Support/AIBurgerClock/logs/quota-polling-diagnostics.json`에 최근 256건·128KiB로 남깁니다. 사용률·계정 정보·CLI 원문은 저장하지 않지만 리셋 시각이 들어 있어 **공개 저장소나 이슈에 그대로 올리지 마세요.** 실행 트리거(수동 Refresh·절전 복귀 등)의 기록은 아니고 다음 예약의 이력입니다. 형식은 [GEMINI_ANTIGRAVITY_QUOTAS](../GEMINI_ANTIGRAVITY_QUOTAS.md#추가-보완-provider별-다음-조회-예약-진단)를 보세요.
- **Mac 검사 추가**: smoke에 Gemini 모델 행 시나리오(막대 7→8→9, 높이, 잘림 없음, 읽기 문구)와 조회 진단 시나리오(예약 이유 5종, 256건·128KiB, 필드 9개, 1분 흔들림 정리)가 들어갔습니다.
- 팝오버 크기(380×821pt)는 모델 행이 없을 때 그대로이고, 메뉴·설정·DB 형식은 바뀌지 않았습니다.

## 0.6.0: 한도 회복 알림 연결

2.5.1 이후 main에 추가되어 Windows 2.6.0에 배포된 기능(#59)의 알림을 Mac에도 연결했습니다. 판정·문구·설정 키는 공통 원본이고 Mac은 메뉴, 알림 전달, 메인 스레드 전환만 맡습니다. [기록](../MACOS_PORT.md#46-한도-회복-알림-연결)

- **켜는 곳**: 오른쪽 클릭(또는 control-클릭) 메뉴의 **한도 회복 알림**. Windows 트레이 메뉴에서 자동 실행 항목 위에 있는 것과 같이 로그인 항목 설정 위에 둡니다. 체크 표시가 현재 상태이고 기본은 꺼짐입니다. 설정은 기존 SQLite의 `QuotaRecoveryNotificationsEnabled`에 저장되며 Windows와 같은 키·값입니다. 저장에 실패하면 기존 설정과 체크를 유지하고 팝오버 피드백에 알립니다.
- **알리는 때**: 앱이 실행 중 받은 정상 한도 응답에서 한 창이 정확히 100%였다가 이후 정상 응답에서 100% 미만이 되면 Provider별로 한 번 알립니다. 첫 응답, 저장된 값 표시, 조회 실패·취소, 재시작 직후는 알리지 않고, 켜거나 끌 때마다 기준을 다시 잡습니다.
- **알림 내용**: 비율·정확한 리셋 시각·계정 값은 넣지 않고 창 이름만 씁니다. 다른 한도가 아직 소진이면 그 안내를 덧붙입니다. 자연 리셋인지 리셋권인지 단정하지 않으며 실제 사용 가능은 보장하지 않습니다.
- **기존 알림이 먼저**: 시간표·공식 상태·공휴일 알림을 먼저 요청하고 한도 알림은 그 뒤 약 6.5초 간격을 둡니다. 대기 중에 다시 소진되거나, 기간·창이 바뀌거나, 조회가 실패한 이전값이 되면 대기 알림을 버립니다.
- **추가 조회 없음**: 조회 주기·절전 복귀·연결 복구 정책은 그대로입니다. 다음 정상 조회에서 발견하므로 실제 회복 시각보다 늦을 수 있습니다.
- **알림 권한**: macOS 알림을 허용하지 않아도 조회와 앱은 그대로 동작합니다. 허용하지 않은 상태에서 켜면 배너가 표시되지 않는다는 안내가 나옵니다.
- 팝오버 높이(380×821pt)와 한도 화면은 그대로입니다.

## 0.5.1: 다크 모드 Gemini 막대 색

다크 모드에서 Gemini 막대의 시간 층(연한 파랑)이 사용 층과 비슷하게 보이던 문제를 고쳤습니다. 다크 모드의 Gemini 사용 색만 `#4285F4`에서 `#5091F7`로 밝아졌고(라이트 모드와 다른 Provider는 그대로), 시간 층과 사용 층의 구분이 ChatGPT·Claude와 같은 정도(2.2:1 이상)가 됩니다. 시간 층의 면 대비 기준(인접 면 1.5:1)은 그대로입니다. [기록](../MACOS_PORT.md#45-051-다크-모드-gemini-막대-색)

## 0.5.0: 한도 막대의 시간 비교

Windows 2.5.0과 같은 공통 변경(#52)을 Mac 막대에 그립니다. 계산과 문구는 공통 원본이고 Mac은 그리기와 VoiceOver 연결만 합니다. [기록](../MACOS_PORT.md#44-050-한도-막대의-시간-층경계선과-voiceover-비교-문구)

- **읽는 법**: 막대의 연한 면은 마지막으로 조회한 시점에 창이 얼마나 지났는지(시간 위치), 진한 면은 사용량, 세로 선은 시간 위치입니다. 진한 면이 선보다 길면 시간보다 빠르게 쓴 것이고 짧으면 느린 것입니다. 소진 예측이나 실제 창 시작 확인이 아니라 조회 시점에 고정한 단순 비교입니다.
- **정확한 값**: 행에 마우스를 올리면 나오는 Provider 상세의 `시간·사용량 비교`에 `시간 경과 40% · 균등 사용 기준보다 15%p 빠름`과 `마지막 조회 기준, 17분 전`이 같이 나옵니다. VoiceOver에서는 값이 있는 한도 행마다 막대가 행 하나의 요소가 되어 행 문구 뒤에 같은 비교를 붙여 한 번만 읽습니다.
- **숨겨지는 경우**: 5시간 창 사용 0%, 리셋 시각·창 길이·성공 시각 미제공, 이전 값, 리셋 시각 경과, 시각 모순에서는 시간 층과 선을 그리지 않고 기존 막대 그대로입니다. 주간 창 0%는 비교합니다.
- **색**: Provider 대표색의 연한 면이며 라이트·다크 각각 바탕에서 계산합니다(시간 층은 인접 면과 1.5:1, 선은 3:1). 라이트 모드의 막대 트랙이 이전보다 약간 밝아졌습니다.
- 막대 높이·행 수·정렬과 팝오버 높이(380×821pt)는 그대로입니다.

## 0.4.1: OpenAI 상태 판정 개선

Windows 2.4.1과 같은 공통 변경입니다(#48). Mac 화면 코드는 바뀌지 않았고 문구와 판정만 공통 원본에서 바뀝니다. [기록](../MACOS_PORT.md#43-041-정리)

- **마지막 확인**: Provider 카드의 Official 줄 끝에 `마지막 확인 MM-dd HH:mm KST`가 붙습니다. 공식 응답을 마지막으로 정상 수신한 시각이며, 서비스 정상이나 서버 데이터의 최신성을 보증하지 않습니다.
- **CHECK와 STALE의 구분**: 응답은 받았지만 incident가 어느 서비스의 것인지 판정하지 못하면 `UNKNOWN / CHECK`이고 확인 시각은 갱신됩니다. 이 사건은 현재 장애로 표시하지도, 정상이라고 단정하지도 않으며 Tooltip의 `범위 미확인 사건`에 따로 나옵니다. STALE은 응답 수신 자체가 실패해 이전 수신 성공에서 15분 이상 지났을 때만 나옵니다. 확인된 장애가 함께 있으면 HOLD/STOP이 우선합니다.
- **ChatGPT 구성 요소**: OpenAI `summary.json`과 `components.json`을 함께 받아 summary에서 빠진 Codex 구성 요소의 장애도 반영합니다. 조회·판정 코드는 Windows와 공통입니다.
- **Tooltip**: `현재 판정`, `최근 조회 시도`, `마지막 확인(응답 수신)`, `최근 응답 수신 실패 이유`, `최근 판정 실패 이유`, `마지막 확인 당시 상태`(시각을 모르면 `(시각 미상)`), `확인된 사건`, `범위 미확인 사건`을 구분해 보여 줍니다. 값이 없는 줄은 숨깁니다.
- 팝오버 높이(380×821pt)와 한도 박스는 그대로입니다.

## 0.4.0: 한도 사용량 막대

Windows 쪽 공통 변경(#45: 사용한 비율 기준 표시·간략 리셋·Provider별 상세 하나)을 Mac 팝오버에 반영했습니다. DB·조회·알림은 그대로입니다. [기록](../MACOS_PORT.md#42-040-한도-사용량-막대)

- **제목**: `개인 계정 잔여 한도`가 공통 제목 `개인 계정 사용량`으로 바뀌었습니다. 행도 `사용` 기준입니다(예: `5시간  42% 사용 · 약 2시간 5분 후 리셋`).
- **사용량 막대**: 한도 행마다 아래에 막대가 붙습니다. 0%는 빈 막대, 100%는 가득 찬 막대이고, 그 사이 값은 최소 2pt로 보입니다. 값이 없는 행(조회 대기·실패)에는 막대가 없습니다.
  - 색은 Windows와 같은 서비스 대표색입니다: ChatGPT `#10A37F`, Claude `#D97757`, Gemini `#4285F4`. 라이트·다크 모두 패널 배경 대비 3:1 이상입니다.
  - 이전 값이거나 리셋 예정 시각이 지난 행은 대표색 대신 회색 톤으로 그립니다.
  - 막대는 읽기 전용입니다. 클릭·hover·메뉴가 없고, 행 글자가 시작하는 x에서 시작합니다. 행 글자가 같은 정보를 이미 읽어 주므로 접근성 요소에서는 뺐습니다.
- **Tooltip**: 한도 박스의 제목·범위·행·막대 어디에 마우스를 올려도 Provider별 상세 하나가 나옵니다. 내용은 정확한 KST 리셋 예정 시각, 실제 복원 확인 조건, 마지막 성공·다음 조회·최근 시도, 오류, 조회 주기·범위입니다. 사용률은 다시 나열하지 않습니다.
- **높이**: 막대 때문에 한도 영역이 약 56pt 늘어, 세 박스 표준 높이는 약 326pt입니다(팝오버 380×821pt). 큰 화면에서는 스크롤 없이 보이고, 짧은 화면에서는 한도 영역만 줄여 스크롤합니다(1280×800은 한도 영역 256pt).

## Mac에서 빌드

먼저 현재 설치 상태를 확인하세요. 빌드 스크립트는 SDK·workload·Xcode·CLI를 설치하거나 로그인하지 않습니다.

```sh
sw_vers
uname -m
xcodebuild -version
command -v dotnet
```

기준 도구는 .NET SDK **10.0.401**, Xcode **27.0**, macos workload set **10.0.401.1**입니다. [Microsoft 공식 Xcode 27 지원 릴리스](https://github.com/dotnet/macios/releases/tag/dotnet-10.0.1xx-xcode27.0-10722)에 맞춘 조합입니다. 프로젝트는 `net10.0-macos27.0` / `osx-arm64`를 대상으로 합니다.

`dotnet`을 찾지 못한다면 [.NET SDK 10.0.401 macOS Arm64 설치 파일](https://dotnet.microsoft.com/en-us/download/dotnet/thank-you/sdk-10.0.401-macos-arm64-installer)을 수동 설치하세요. Runtime만 설치하거나 x64 버전을 선택하지 않습니다. 설치 후 새 터미널에서 버전을 확인합니다.

```sh
dotnet --version
```

`10.0.401`이 확인되면 macOS 앱 빌드에 필요한 workload만 설치합니다. 이 명령은 개발 도구를 설치하며 계정 로그인이나 앱 자동 실행 설정을 바꾸지 않습니다. 시스템에 설치한 SDK는 관리자 권한이 필요할 수 있어 `sudo`를 사용합니다.

```sh
sudo dotnet workload install macos --version 10.0.401.1
dotnet workload list
```

Xcode가 설치되어 있지만 개발 도구 경로·라이선스 오류가 나오면 실제 메시지를 확인한 뒤 처리합니다. 이 앱의 스크립트가 Xcode 설정을 임의 변경하거나 라이선스를 대신 승인하지 않습니다.

소스가 아직 없으면 저장소를 받습니다. Mac 앱은 2026-10-04부터 main에 있습니다. 이미 저장소가 있다면 변경사항을 보존하고 main을 최신으로 받으세요(`git pull --ff-only`).

```sh
git clone https://github.com/hydron75/ai-burger-clock.git
cd ai-burger-clock
bash Mac/build.sh
```

스크립트는 공통 코드의 가짜 응답/임시 DB 검사를 먼저 실행하고, 경고를 오류로 취급해 네이티브 Release를 빌드합니다. 이후 bundle의 서명 검증과 SQLite 네이티브 라이브러리 포함 여부를 확인합니다. 앱·계정 조회를 자동 실행하지는 않습니다.

앱 빌드는 **sudo 없이** 실행합니다. 기본 NuGet HTTP 캐시는 저장소의 `artifacts/mac-build/nuget-http-cache`에 두고 Git에서는 제외합니다. 사용자가 `NUGET_HTTP_CACHE_PATH`를 지정했다면 그 경로를 그대로 사용합니다. 취약성 검사·패키지 저장소 설정·전역 패키지 캐시는 변경하지 않습니다.

### 실행 중인 앱이 있을 때

빌드는 `Mac/bin/Release/.../AI Burger Clock.app`을 그 자리에서 덮어씁니다. 같은 bundle로 앱이 실행 중이면 실행 중인 앱이 바뀐 코드·리소스를 읽게 되므로, `build.sh`는 빌드 전에 이 경로에서 실행 중인 프로세스를 찾습니다. `/Applications` 등 다른 위치의 앱은 대상이 아닙니다.

- 터미널에서 직접 실행하면 `종료하고 빌드할까요? [y/N]`를 묻습니다. `y`면 그 PID에만 일반 종료를 요청하고(저장 대기 중인 기록을 마친 뒤 종료), 20초 안에 끝나면 빌드를 계속합니다. `N`·Enter·Ctrl-D면 빌드하지 않고 종료 코드 2로 멈춥니다.
- 질문할 수 없는 환경(파이프·자동화 도구)에서는 묻지 않고 경고 후 종료 코드 2로 멈춥니다.
- `bash Mac/build.sh --quit-running`은 묻지 않고 종료를 요청한 뒤 빌드합니다.
- 종료 요청이 실패하거나 20초 안에 끝나지 않으면 빌드를 시작하지 않고 종료 코드 2로 멈춥니다. 앱을 메뉴바 아이콘 오른쪽 클릭 → 종료로 닫고 다시 실행하세요.

### Xcode와 워크로드가 요구하는 버전이 다를 때 (`--allow-xcode-mismatch`)

.NET macOS 워크로드는 자신이 요구하는 Xcode의 major.minor와 설치된 Xcode가 다르면 `E0191`(예: `requires Xcode 27.0. The current version of Xcode is 27.1`)로 빌드를 멈춥니다. Xcode가 먼저 올라가고 워크로드가 늦게 따라오는 기간에 생기며, 새 워크로드가 나오기 전에는 워크로드 갱신으로 해결되지 않습니다.

`bash Mac/build.sh --allow-xcode-mismatch`는 **이 버전 검사 하나만** 건너뜁니다(`-p:ValidateXcodeVersion=false`). 다른 검사와 경고를 오류로 취급하는 설정, 서명 검증은 그대로입니다. `--quit-running`과 함께 쓸 수 있습니다.

- **기본은 꺼짐입니다.** 옵션이 없으면 지금처럼 `E0191`로 멈추고 아무것도 기록하지 않습니다.
- **켜면** 터미널에 `지원되지 않는 Xcode 조합으로 빌드합니다. smoke와 실제 동작을 확인한 뒤 사용하세요.`와 함께 Xcode 버전(build 번호), 워크로드 버전과 그것이 요구하는 Xcode, .NET SDK, git 커밋을 보여 주고, 같은 내용을 `artifacts/mac-build/xcode-mismatch.log`(Git에서 제외)에 시각과 함께 한 줄 남깁니다. 빌드가 끝나면 종료 코드도 한 줄 더 남기고, 성공했다면 기록하라는 참고 문구를 다시 보여 줍니다.
- **불필요하게 켠 경우**(두 버전이 같음)에는 검사를 건너뛰지 않고 평소처럼 빌드하며, "필요하지 않다"는 알림과 로그 한 줄만 남깁니다.
- 워크로드가 요구하는 Xcode 버전은 설치된 macOS SDK 팩(`Microsoft.macOS.Sdk.Versions.props`)에서 읽고, 워크로드와 같게 **major.minor만** 비교합니다(예: 요구값 `27.0.1`은 `27.0`으로 봅니다). 읽지 못하면 "unknown"으로 기록하고 요청대로 건너뜁니다.
- Xcode가 한 major 이상 앞서가서 **27이 아닌 더 높은 버전**(예: 28)이면, 옵션이 없을 때는 스크립트의 `Xcode 27` 사전 검사에서 멈춥니다. 옵션을 켜면 이 사전 검사를 통과시키고 "Xcode major가 27이 아님"을 경고·로그에 덧붙인 채 계속합니다. macOS 27 SDK가 없으면 이후 빌드가 실패하며, 그 판단은 이후 빌드 검사에 맡깁니다. 27보다 낮은 Xcode는 옵션을 켜도 통과시키지 않습니다.

**기록 규칙:** 이 옵션으로 만든 빌드를 실제로 쓰게 되면(앱 교체, 배포, 또는 그 빌드의 결과를 PR·기록의 근거로 쓸 때) 해당 `MACOS_PORT.md` 절의 "이 Mac에서 수행한 검증" 표에 다음을 적습니다.

1. `--allow-xcode-mismatch`를 사용했다는 사실.
2. Xcode 버전과 build 번호, .NET macOS 워크로드 버전과 그것이 요구하는 Xcode, .NET SDK 버전(`xcodebuild -version`, `dotnet workload list`, 위 로그 한 줄).
3. 같은 조건에서 확인한 결과: smoke 종료 코드, 가능하면 같은 조건으로 만든 직전 main 기준선의 smoke 결과.
4. 로그 파일은 로컬에만 있으므로 위 내용을 문서에 직접 옮깁니다. 문서에는 계정 값이나 로컬 절대 경로를 적지 않습니다.

임시 사본으로 검증만 할 때도 같은 옵션을 쓰고, 그 결과를 PR 코멘트에 적을 때는 "Xcode ○○ + 워크로드 ○○, 버전 검사 건너뜀"을 함께 밝힙니다. 워크로드가 새 Xcode를 지원하게 되면 이 옵션은 쓰지 않습니다.

### 출력 없이 종료 / CommandLineTools 선택

소스 `91c32c6`의 빌드에서 `xcodebuild -version` 단계가 실패했지만 오류를 숨겨 조용히 종료한 사례가 있습니다. 최신 스크립트는 시작과 도구 확인 단계를 즉시 표시하고, Xcode·SDK·workload 조회 실패 시 원래 오류를 보존한 채 종료 코드 2로 멈춥니다. 이 경우 공통 검사와 앱 컴파일은 시작하지 않습니다.

`active developer directory '/Library/Developer/CommandLineTools' is a command line tools instance`가 나오면 전체 Xcode 대신 독립 Command Line Tools가 선택된 상태입니다. Command Line Tools 27을 설치하는 것과 전체 Xcode 27을 빌드 도구로 선택하는 것은 다릅니다. 먼저 아래 두 줄을 **각각** 실행해 실제 오류와 선택 경로를 확인합니다.

```sh
/usr/bin/xcodebuild -version
/usr/bin/xcode-select -p
```

전체 Xcode가 기본 위치에 있다면 다음 조회로 확인합니다. 2026-10-03 사용자 Mac에서 이 경로의 Xcode 27.0 / build 27A266a를 확인했습니다.

```sh
/usr/bin/env DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer /usr/bin/xcodebuild -version
```

이 조회가 성공하면 실행 중인 앱을 종료한 뒤 저장소 루트에서 다음 두 줄을 각각 실행합니다. Xcode가 다른 위치에 설치됐다면 확인된 실제 경로로 바꿉니다.

```sh
git pull --ff-only
/usr/bin/env DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer /bin/bash Mac/build.sh
```

`DEVELOPER_DIR`는 이 빌드와 자식 프로세스에만 적용합니다. 전역 `xcode-select` 설정·라이선스·설치 상태를 바꾸지 않습니다. 스크립트가 Xcode를 자동 선택하거나 설치하지도 않습니다. [Apple의 개발 도구 선택 안내](https://developer.apple.com/documentation/xcode/configuring-command-line-tools-settings), [원인과 검증 기록](../MACOS_PORT.md#16-xcode-선택-경로와-조용한-빌드-중단-보완).

이 실행별 지정으로 소스 `9f805f8`의 실제 Mac 0.1.1 Release·공통 검사·서명·ARM64 SQLite 확인까지 성공했고 해당 bundle의 native smoke도 종료 코드 0으로 통과했습니다. 기본 선택 경로를 전역으로 바꾼 결과로 해석하지 않습니다.

### NU1900 / HTTP 캐시 접근 거부

첫 Mac 빌드에서 사용자 홈의 NuGet HTTP 캐시에 접근하지 못해 취약성 데이터 조회가 실패한 사례가 있습니다. 관리자 권한으로 개발 도구를 설치하면서 캐시 소유권이 달라졌을 가능성이 있지만, 소유권을 확인하기 전에는 확정할 수 없습니다.

최신 preview를 받아 일반 사용자로 다시 빌드하세요. 저장소 루트에서 실행합니다.

```sh
git pull --ff-only
bash Mac/build.sh
```

업데이트 전에 한 번만 캐시 경로를 지정해서 실행할 수도 있습니다.

```sh
NUGET_HTTP_CACHE_PATH="$PWD/artifacts/mac-build/nuget-http-cache" bash Mac/build.sh
```

이 방법은 기존 캐시를 삭제하거나 권한을 바꾸지 않습니다. `NuGetAudit=false`·경고 무시·`sudo bash Mac/build.sh`로 문제를 숨기지 않습니다. 접근 거부가 다른 경로에서도 나오면 해당 오류와 경로를 확인한 뒤 별도로 진단합니다. 2026-10-03 KST 재시도에서 공통 검사 244,338건이 통과해 이 캐시 문제 해결은 확인했습니다. [NuGet 캐시 경로 공식 안내](https://learn.microsoft.com/en-us/nuget/consume-packages/managing-the-global-packages-and-cache-folders)

### IL2026 / 한도 캐시 JSON

공통 검사 이후 `UsageStore.cs`의 JSON 저장·읽기에서 IL2026이 나오면 최신 main 소스를 받아 위와 같이 다시 빌드하세요. Apple SDK의 trimming 검사에서 런타임 reflection 기반 직렬화를 경고하는 문제였으며, `QuotaJsonContext`로 타입 정보를 미리 생성하도록 수정했습니다. JSON 형식·기존 캐시·DB schema 2는 유지하고, 경고 억제나 새 NuGet 패키지는 추가하지 않았습니다. [Microsoft source generation 안내](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation)

수정 후 Windows의 Release/회귀·공통 검사, Mac 참조 코드의 trimming 분석과 reflection 비활성화 캐시 검사를 통과했습니다. 이어서 소스 `302aee8`의 **실제 Mac `.app` 빌드·서명 검사와 native smoke까지 통과**했고 CLI 설치 후 실제 한도 수신도 확인했습니다. 별도 UI 수정본 0.1.1의 소스 `9f805f8`도 새 Mac 빌드·서명·ARM64 SQLite와 새 native smoke를 통과했으며 일반 실행 한 화면 표시도 확인했습니다. [이전 native 검사 범위](../MACOS_PORT.md#13-실제-mac-native-smoke-통과), [새 빌드 결과](../MACOS_PORT.md#17-011-실제-mac-release-재빌드-성공), [새 native 검사](../MACOS_PORT.md#18-011-새-native-smoke-통과).

## 데이터와 자동 실행

DB는 아래 Mac 전용 위치에 생성됩니다. Windows의 기존 DB·레지스트리·배포 경로는 건드리지 않습니다.

```text
~/Library/Application Support/AIBurgerClock/burgerclock.db
```

공휴일 옵션과 정규화한 최근 한도 캐시는 기존 schema 2의 metadata에 저장됩니다. Prompt·AI 답변·인증 정보는 저장하지 않습니다. 로그인 자동 실행을 켜기 전에 `.app`를 `/Applications` 등 고정된 위치에 두세요. macOS의 `SMAppService.MainApp`로 등록하고, 승인이 필요하면 시스템 설정 → 일반 → 로그인 항목에서 확인합니다. 다른 경로로 앱을 옮겼으면 해당 설정을 다시 확인하세요.

알림은 최초 실행 시 macOS 권한을 요청합니다. 허용하지 않아도 시간표와 조회는 계속 동작합니다. 시스템 설정 → 알림에서 AI Burger Clock을 관리할 수 있습니다. 집중 모드·알림 정책으로 배너가 보이지 않을 수 있습니다.

Mac에서 사용하는 Codex와 Claude는 **그 Mac에 별도로 설치·로그인되어 있어야** 합니다. Windows의 로그인 상태는 자동 복사하지 않습니다. CLI가 없거나 조회에 실패하면 앱은 이전값/조회 불가를 표시하고 다른 기능은 유지합니다.

## Gemini 한도(agy)

Gemini 한도는 공식 Antigravity CLI `agy`의 내장 명령 결과를 읽습니다(#30, 공통 코드).

- 먼저 `agy --version`을 실행해 **1.3.1 이상·2.0 미만 안정 버전**인지 확인합니다. 그 밖의 버전, 사전 배포 버전, 알 수 없는 출력이면 조회하지 않고 안내만 표시합니다.
- 이어서 `agy -p /usage --output-format json --print-timeout 20s`를 셸 없이 절대 경로로 실행합니다. 이때 CLI 자동 업데이트는 꺼 둡니다(`AGY_CLI_DISABLE_AUTO_UPDATE=true`).
- 결과에서 `Gemini Models` 그룹의 5시간·주간 창을 쓰고, 0.7.0부터는 모델 전용 주간 묶음(#62)도 별도 행으로 씁니다(범위 밖 묶음과 형식이 모순된 응답은 버립니다). 잔여율은 `remaining_fraction × 100`이고, 리셋은 UTC로 저장해 KST로 표시합니다.
- 정상 종료, `SUCCESS`, 빈 대화 ID, 0턴, 토큰 0을 확인합니다. 모델 요청이 일어난 응답이나 형식이 바뀐 응답은 버리고, 이전 성공값을 "이전" 표시로 보여 줍니다.
- 앱은 agy의 로그인 정보·토큰을 읽지 않습니다. 로그인은 터미널에서 agy로 먼저 마칩니다. agy 실행 중 기존 hooks/MCP 설정이 읽힐 수 있다는 제한은 사용자가 받아들인 조건입니다.
- 조회 주기(기본 1시간, #68)와 실패 재시도는 Codex·Claude와 같습니다. 단 Gemini의 사용 0% 창은 5분 간격 빠른 조회 기준에서 제외합니다(0.7.0, #63). 2026-10-09 이 Mac(agy 1.3.2)에서 한 번 조회에 약 8초가 걸렸습니다.

### 설치 경로 제약 (중요)

Finder 더블클릭이나 로그인 항목으로 실행된 앱은 터미널의 PATH를 받지 못합니다(launchd 기본값 `/usr/bin:/bin:/usr/sbin:/sbin`). 그래서 앱은 PATH 대신 다음 세 폴더를 항상 함께 확인합니다.

- `~/.local/bin`
- `/opt/homebrew/bin`
- `/usr/local/bin`

**`agy`(그리고 `codex`·`claude`)가 이 세 폴더 밖에 있으면 Finder·로그인 항목으로 실행한 앱은 찾지 못합니다.** 예: `~/bin`, `~/.npm-global/bin`. 이때 Gemini 한도 박스에 `공식 CLI를 찾지 못했습니다. 설치 경로를 확인하세요.`가 나옵니다(이전 성공값이 있으면 그 값을 "이전"으로 함께 표시). 터미널에서 `open`으로 실행하면 터미널 PATH가 넘어가서 찾을 수 있으므로, 터미널 실행만으로는 이 문제를 확인할 수 없습니다. 해결하려면 실행 파일을 위 폴더 중 하나에 두거나 링크합니다. 예: `ln -s ~/bin/agy ~/.local/bin/agy`.

## CLI를 찾지 못하는 경우

첫 일반 실행 스크린샷에서는 두 계정 한도에 `공식 CLI를 찾지 못했습니다`가 표시됐고, 이후 사용자가 CLI를 설치해 정상 수신했습니다. 이 메시지는 인증 응답이 아니라 실행 파일 탐색 실패입니다. 다른 설치에서 같은 문제가 생기면 미설치·GUI에 보이지 않는 설치 경로·실행 권한을 구분합니다.

앱은 GUI 프로세스의 PATH와 `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`을 확인합니다(위 "설치 경로 제약"). 아래 결과가 이 세 폴더 밖이면 Finder·로그인 항목 실행에서는 찾지 못합니다. 터미널의 셸 프로필은 읽거나 실행하지 않으므로 터미널에서 명령이 보여도 GUI 앱에는 안 보일 수 있습니다. 먼저 맥 터미널에서 아래 읽기 전용 확인 결과를 확인하세요.

```sh
for task_cli in codex claude agy node npm
do
  printf '%s: ' "$task_cli"
  command -v "$task_cli" || printf '없음\n'
done
```

이 명령은 설치 경로만 읽으며 CLI 실행·계정 조회·로그인·설치·설정 변경을 하지 않습니다. 정상 수신 중이면 반복할 필요가 없습니다. `.app 위치 확인 필요`라는 자동 실행 문구는 별도 항목이며, 한도 조회 실패와 혼동하지 않습니다.

- [ServiceManagement 바인딩](https://github.com/dotnet/macios/blob/dotnet-10.0.1xx-xcode27.0-10722/src/servicemanagement.cs): SMAppService.
- [UserNotifications 바인딩](https://github.com/dotnet/macios/blob/dotnet-10.0.1xx-xcode27.0-10722/src/usernotifications.cs): UNUserNotificationCenter.

공통 기능 개선은 루트의 원본 소스에서 반영하며 Mac 고유 UI·로그인 항목·알림 코드는 이 폴더에서 관리합니다. 이 preview는 Windows 기능 변경이나 기존 배포본 교체를 동반하지 않습니다.
